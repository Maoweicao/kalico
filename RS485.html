    RS485 Servo Support¶

    This document describes Kalico's support for RS485 servo drives using Modbus RTU and custom protocols. RS485 allows using industrial servo motors with position feedback over a half-duplex serial bus.

    Overview¶

    RS485 is a physical layer standard for serial communication. Unlike step/dir signaling, RS485 sends position setpoints and receives actual position data over a shared bus. Kalico supports multiple protocols running on top of RS485:

    • Modbus RTU — Industry standard protocol (CiA 402 register mapping)
    • UART Passthrough — Raw byte-level communication for custom protocols
    • Custom Protocols — User-written Python classes for vendor-specific drives

    Hardware Requirements¶

    RS485 Adapter (host transport)¶

    For the default host transport you need an RS485 adapter connected to your host computer. Common options:

    • FTDI FT232RL + MAX485: Automatic direction control via CBUS pin
    • CH340 + MAX485: Direction control via RTS signal
    • USB-to-RS485 converter: Pre-built adapters with auto-direction

    Alternatively, with rs485_transport: mcu no adapter is needed at all: the micro-controller bit-bangs the Modbus RTU bus on a single GPIO pin (see MCU transport below).

    Wiring (host transport)¶

    Host ─── USB-to-RS485 ─── RS485 Bus ─── Servo Drive
         │                │
         │  A ─────────── A (Data-)
         │  B ─────────── B (Data+)
         │  GND ───────── GND
         │
         └── 120Ω termination resistor at each end of bus

    Servo Drive¶

    Any servo drive that supports Modbus RTU or a custom RS485 protocol:

    • Leadshine ES/EC series — Modbus RTU with custom register map
    • Delta ASDA series — Modbus RTU
    • Panasonic MINAS series — Modbus RTU
    • Generic RS485 servos — Via UART passthrough

    MCU Transport¶

    With rs485_transport: mcu the bus is bit-banged by the micro-controller itself on a single GPIO pin, so no USB-to-RS485 adapter is required. This uses the same firmware software Modbus UART (src/modbus_uart.c) as the LYX stepper drivers; both may share the same bus.

    MCU GPIO ──── servo drive communication pin
MCU GND  ──── servo drive GND
    • The firmware must be built with the "Support software Modbus RTU UART communication" option enabled.
    • The pin is a half-duplex single-wire 8N1 UART at the configured baud rate. Each rs485_slave_id must be unique across all Modbus devices sharing the pin.
    • Only the modbus_rtu protocol is supported on the MCU transport; uart_passthrough and custom protocols still require the host transport.
    • A single FC03 read is limited to 5 registers (the firmware receive buffer is 16 bytes).

    Configuration¶

    Modbus RTU (Default)¶

    [rs485_stepper x]
serial_port: /dev/ttyUSB0

rs485_protocol: modbus_rtu
rs485_slave_id: 1

endstop_pin: ^PC1

    UART Passthrough¶

    [rs485_stepper y]

    Writing Custom Protocols¶

    To write a custom protocol for your servo drive, subclass RS485Protocol from klippy.extras.rs485.protocol:

    # File: klippy/extras/my_servo_rs485.py
from klippy.extras.rs485.modbus_rtu import ModbusRtuProtocol

class MyServoProtocol(ModbusRtuProtocol):
    """Custom protocol for MyServo RS485 drives."""

    # Register addresses (check your drive manual)
    REG_CONTROL = 0x0000
    REG_STATUS = 0x0001
    REG_TARGET_POS_L = 0x0010
    REG_TARGET_POS_H = 0x0011
    REG_ACTUAL_POS_L = 0x0012
    REG_ACTUAL_POS_H = 0x0013

    def set_target_position(self, position):
        pos_u = position & 0xFFFFFFFF
        self.write_register(self.REG_TARGET_POS_L, pos_u & 0xFFFF)
        self.write_register(self.REG_TARGET_POS_H, (pos_u >> 16) & 0xFFFF)

    def get_actual_position(self):
        lo = self.read_register(self.REG_ACTUAL_POS_L)
        hi = self.read_register(self.REG_ACTUAL_POS_H)
        pos = (hi << 16) | lo
        if pos >= 0x80000000:
            pos -= 0x100000000
        return pos

    def set_control_word(self, value):
        self.write_register(self.REG_CONTROL, value & 0xFFFF)

    def get_status_word(self):
        return self.read_register(self.REG_STATUS)

    def get_state_name(self):
        sw = self.get_status_word()
        if sw & (1 << 3): return "FAULT"
        if sw & (1 << 2): return "OPERATION_ENABLED"
        if sw & (1 << 1): return "SWITCHED_ON"
        if sw & (1 << 0): return "READY_TO_SWITCH_ON"
        return "UNKNOWN"

    Then reference it in your config:

    [rs485_stepper x]
rs485_protocol: custom
protocol_class: my_servo_rs485.MyServoProtocol
# ...

    Protocol Interface¶

    Your custom protocol must implement these methods:

    Method Description
    read_register(register) Read a register, return integer value
    write_register(register, value) Write a register with integer value
    set_target_position(position) Set target position (encoder counts)
    get_actual_position() Get actual position (encoder counts)
    set_control_word(value) Set the drive control word
    get_status_word() Get the drive status word
    get_error_code() Get drive error code (optional)
    get_state_name() Get human-readable state name (optional)

    Modbus RTU Register Mapping¶

    The default register map uses standard CiA 402 addresses:

    Register Address Description
    Controlword 0x6040 Drive control
    Statusword 0x6041 Drive status
    Target Position 0x607A Position command (32-bit)
    Actual Position 0x6064 Position feedback (32-bit)
    Mode of Operation 0x6060 Operating mode
    Error Code 0x603F Error code

    Custom register addresses can be specified in the config:

    [rs485_stepper x]
register_control_word: 0x0000
register_status_word: 0x0001
register_target_position: 0x0010
register_actual_position: 0x0012

    Modbus RTU Frame Format¶

    Request:  [SlaveID(1)] [FC(1)] [StartAddr(2)] [Count(2)] [CRC16(2)]
Response: [SlaveID(1)] [FC(1)] [ByteCount(1)] [Data(N)] [CRC16(2)]

FC03 (Read Holding Registers):
  Request:  01 03 00 10 00 02 C5 CF
  Response: 01 03 04 03 E8 00 00 XX XX

FC06 (Write Single Register):
  Request:  01 06 60 40 00 0F XX XX
  Response: 01 06 60 40 00 0F XX XX

FC16 (Write Multiple Registers):
  Request:  01 10 60 7A 00 02 04 03 E8 00 00 XX XX
  Response: 01 10 60 7A 00 02 XX XX

    Troubleshooting¶

    No response from drive¶

    1. Check wiring (A/B polarity, GND connection)
    2. Verify baud rate matches drive setting
    3. Check slave ID matches drive configuration
    4. Ensure termination resistors are installed

    CRC errors¶

    1. Check for noise on the RS485 bus
    2. Verify cable length (max ~1200m at 9600 baud)
    3. Try lower baud rate
    4. Check ground connection between devices

    Position drift¶

    1. Verify encoder is working correctly
    2. Check that rotation_distance matches your mechanics
    3. Ensure the drive is in the correct operating mode

    Custom protocol not loading¶

    1. Verify the Python file is in klippy/extras/
    2. Check the protocol_class path is correct
    3. Ensure the class inherits from RS485Protocol or ModbusRtuProtocol
