# 协议

Kalico 消息传递协议用于 Kalico 主机软件和 Kalico 微控制器软件之间的底层通信。从高级层面来看，该协议可以被视为一系列命令和响应字符串，这些字符串经过压缩、传输，然后在接收端进行处理。未压缩的人类可读格式的命令系列示例可能如下所示：

```
set_digital_out pin=PA3 value=1
set_digital_out pin=PA7 value=1
schedule_digital_out oid=8 clock=4000000 value=0
queue_step oid=7 interval=7458 count=10 add=331
queue_step oid=7 interval=11717 count=4 add=1281
```

有关可用命令的信息，请参阅 [mcu 命令](MCU_Commands.md) 文档。有关如何将 G-Code 文件转换为相应的人类可读微控制器命令的信息，请参阅[调试](Debugging.md)文档。

本页提供了 Kalico 消息传递协议本身的高级描述。它描述了消息如何声明、以二进制格式编码（"压缩"方案）以及如何传输。

该协议的目标是在主机和微控制器之间启用一个无错误的通信通道，该通道具有低延迟、低带宽和微控制器的低复杂性。

## 微控制器接口

Kalico 传输协议可以被视为微控制器和主机之间的 [RPC](https://en.wikipedia.org/wiki/Remote_procedure_call) 机制。微控制器软件声明主机可以调用的命令以及它可以生成的响应消息。主机使用该信息来命令微控制器执行操作并解释结果。

### 声明命令

微控制器软件通过在 C 代码中使用 DECL_COMMAND() 宏来声明"命令"。例如：

```
DECL_COMMAND(command_update_digital_out, "update_digital_out oid=%c value=%c");
```

上述声明了一个名为"update_digital_out"的命令。这允许主机"调用"该命令，这将导致微控制器中的 command_update_digital_out() C 函数被执行。上述还表明该命令接受两个整数参数。当 command_update_digital_out() C 代码被执行时，它将被传递一个包含这两个整数的数组 - 第一个对应于 'oid'，第二个对应于 'value'。

通常，参数使用 printf() 风格的语法描述（例如，"%u"）。格式直接对应于命令的人类可读视图（例如，"update_digital_out oid=7 value=1"）。在上面的示例中，"value=" 是参数名称，"%c" 表示参数是整数。在内部，参数名称仅用作文档。在此示例中，"%c" 也用作文档来指示预期的整数为 1 字节大小（声明的整数大小不会影响解析或编码）。

微控制器构建将收集所有使用 DECL_COMMAND() 声明的命令，确定它们的参数，并安排它们可被调用。

### 声明响应

为了从微控制器向主机发送信息，会生成"响应"。这些响应都使用 sendf() C 宏进行声明和传输。例如：

```
sendf("status clock=%u status=%c", sched_read_time(), sched_is_shutdown());
```

上述传输了一个包含两个整数参数（"clock" 和 "status"）的"status"响应消息。微控制器构建会自动查找所有 sendf() 调用并为它们生成编码器。sendf() 函数的第一个参数描述响应，其格式与命令声明相同。

主机可以安排为每个响应注册一个回调函数。因此，实际上，命令允许主机在微控制器中调用 C 函数，而响应允许微控制器软件在主机中调用代码。

sendf() 宏应仅从命令或任务处理程序中调用，不应从中断或定时器中调用。代码不需要为了响应接收到的命令而发出 sendf()，它不受 sendf() 可调用次数的限制，并且可以在任务处理程序中的任何时间调用 sendf()。

#### 输出响应

为了简化调试，还有一个 output() C 函数。例如：

```
output("The value of %u is %s with size %u.", x, buf, buf_len);
```

output() 函数的用法类似于 printf() - 它旨在生成和格式化供人类使用的任意消息。

### 声明枚举

枚举允许主机代码对微控制器作为整数处理的参数使用字符串标识符。它们在微控制器代码中声明 - 例如：

```
DECL_ENUMERATION("spi_bus", "spi", 0);

DECL_ENUMERATION_RANGE("pin", "PC0", 16, 8);
```

如果第一个示例，DECL_ENUMERATION() 宏为任何具有参数名称为 "spi_bus" 或参数名称后缀为 "_spi_bus" 的命令/响应消息定义枚举。对于这些参数，字符串 "spi" 是一个有效值，它将被传输为整数值零。

也可以声明枚举范围。在第二个示例中，"pin" 参数（或任何后缀为 "_pin" 的参数）将接受 PC0、PC1、PC2、...、PC7 作为有效值。这些字符串将被传输为整数 16、17、18、...、23。

### 声明常量

也可以导出常量。例如，以下内容：

```
DECL_CONSTANT("SERIAL_BAUD", 250000);
```

将从微控制器向主机导出一个名为 "SERIAL_BAUD"、值为 250000 的常量。也可以声明一个字符串常量 - 例如：

```
DECL_CONSTANT_STR("MCU", "pru");
```

## 底层消息编码

为了实现上述 RPC 机制，每个命令和响应都以二进制格式编码进行传输。本节描述传输系统。

### 消息块

从主机发送到微控制器以及反向的所有数据都包含在"消息块"中。消息块具有两个字节的头部和三个字节的尾部。消息块的格式为：

```
<1 字节长度><1 字节序列><n 字节内容><2 字节 crc><1 字节同步>
```

长度字节包含消息块中的字节数，包括头部和尾部字节（因此最小消息长度为 5 字节）。当前最大消息块长度为 64 字节。序列字节在低序位中包含 4 位序列号，高序位始终包含 0x10（高序位保留供将来使用）。内容字节包含任意数据，其格式在下一节中描述。crc 字节包含消息块（包括头部字节但不包括尾部字节）的 16 位 CCITT [CRC](https://en.wikipedia.org/wiki/Cyclic_redundancy_check)。同步字节为 0x7e。

消息块的格式受 [HDLC](https://en.wikipedia.org/wiki/High-Level_Data_Link_Control) 消息帧的启发。与 HDLC 一样，消息块可以选择性地在块开头包含额外的同步字符。与 HDLC 不同，同步字符不是帧独有的，可以出现在消息块内容中。

### 消息块内容

从主机发送到微控制器的每个消息块在其内容中包含一系列零个或多个消息命令。每个命令以一个 [可变长度数量](#variable-length-quantities)（VLQ）编码的整数命令 ID 开始，后跟零个或多个给定命令的 VLQ 参数。

例如，以下四个命令可以放在单个消息块中：

```
update_digital_out oid=6 value=1
update_digital_out oid=5 value=0
get_config
get_clock
```

并编码为以下八个 VLQ 整数：

```
<id_update_digital_out><6><1><id_update_digital_out><5><0><id_get_config><id_get_clock>
```

为了编码和解析消息内容，主机和微控制器必须就命令 ID 和每个命令的参数数量达成一致。因此，在上面的示例中，主机和微控制器都知道 "id_update_digital_out" 后面总是跟两个参数，而 "id_get_config" 和 "id_get_clock" 没有参数。主机和微控制器共享一个"数据字典"，该字典将命令描述（例如，"update_digital_out oid=%c value=%c"）映射到其整数命令 ID。在处理数据时，解析器将知道在给定命令 ID 之后预期有多少个 VLQ 编码参数。

从微控制器发送到主机的消息块的内容遵循相同的格式。这些消息中的标识符是"响应 ID"，但它们具有相同的用途并遵循相同的编码规则。实际上，从微控制器发送到主机的消息块在消息块内容中从不包含多个响应。

#### 可变长度数量

有关 VLQ 编码整数的一般格式的更多信息，请参阅 [wikipedia 文章](https://en.wikipedia.org/wiki/Variable-length_quantity)。Kalico 使用一种支持正数和负数的编码方案。接近零的整数使用较少的字节进行编码，正整数通常比负整数使用较少的字节进行编码。下表显示了每个整数编码所需的字节数：

| 整数                      | 编码大小 |
|---------------------------|----------|
| -32 .. 95                 | 1        |
| -4096 .. 12287            | 2        |
| -524288 .. 1572863        | 3        |
| -67108864 .. 201326591    | 4        |
| -2147483648 .. 4294967295 | 5        |

#### 可变长度字符串

作为上述编码规则的例外，如果命令或响应的参数是动态字符串，则该参数不会被编码为简单的 VLQ 整数。相反，它通过将长度作为 VLQ 编码的整数传输，后跟内容本身来进行编码：

```
<VLQ 编码长度><n 字节内容>
```

数据字典中找到的命令描述允许主机和微控制器知道哪些命令参数使用简单的 VLQ 编码，哪些参数使用字符串编码。

## 数据字典

为了在微控制器和主机之间建立有意义的通信，双方必须就"数据字典"达成一致。该数据字典包含命令和响应的整数标识符及其描述。

微控制器构建使用 DECL_COMMAND() 和 sendf() 宏的内容来生成数据字典。构建会自动为每个命令和响应分配唯一的标识符。该系统允许主机和微控制器代码无缝使用描述性的人类可读名称，同时仍使用最小带宽。

主机在首次连接到微控制器时查询数据字典。一旦主机从微控制器下载了数据字典，它就会使用该数据字典来编码所有命令并解析来自微控制器的所有响应。因此，主机必须处理动态数据字典。但是，为了保持微控制器软件简单，微控制器始终使用其静态（编译时）数据字典。

数据字典通过向微控制器发送"identify"命令进行查询。微控制器将以"identify_response"消息响应每个 identify 命令。由于在获取数据字典之前需要这两个命令，因此它们的整数 ID 和参数类型在微控制器和主机中都是硬编码的。"identify_response"响应 ID 为 0，"identify"命令 ID 为 1。除了具有硬编码的 ID 之外，identify 命令及其响应的声明和传输方式与其他命令和响应相同。没有其他命令或响应是硬编码的。

传输的数据字典本身的格式是一个 zlib 压缩的 JSON 字符串。微控制器构建过程生成该字符串，对其进行压缩，并将其存储在微控制器闪存的文本部分中。数据字典可能比最大消息块大小大得多 - 主机通过发送多个 identify 命令请求数据字典的渐进块来下载它。一旦获得所有块，主机组装这些块，解压缩数据并解析内容。

除了通信协议信息外，数据字典还包含软件版本、枚举（由 DECL_ENUMERATION 定义）和常量（由 DECL_CONSTANT 定义）。

## 消息流

从主机发送到微控制器的消息命令旨在是无错误的。微控制器将检查每个消息块中的 CRC 和序列号，以确保命令准确且按顺序。微控制器始终按顺序处理消息块 - 如果收到乱序的块，它将丢弃该块以及任何其他乱序块，直到收到具有正确序列的块。

底层主机代码实现了针对丢失和损坏的消息块的自动重传系统。为此，微控制器在每个成功接收的消息块之后传输"ack 消息块"。主机在发送每个块之后安排一个超时，如果超时到期而未收到相应的"ack"，它将重新传输。此外，如果微控制器检测到损坏或乱序的块，它可能会传输"nak 消息块"以促进快速重传。

"ack"是具有空内容（即 5 字节消息块）且序列号大于最后接收的主机序列号的消息块。"nak"是具有空内容且序列号小于最后接收的主机序列号的消息块。

该协议促进"窗口"传输系统，以便主机可以同时有许多未完成的消息块在传输中。（这超出了给定消息块中可能存在的许多命令。）这允许在传输延迟的情况下实现最大带宽利用率。超时、重传、窗口和 ack 机制受 [TCP](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) 中类似机制的启发。

在另一个方向上，从微控制器发送到主机的消息块旨在是无错误的，但它们没有保证传输。（响应不应损坏，但它们可能会丢失。）这样做是为了保持微控制器中的实现简单。响应没有自动重传系统 - 高级代码应能够处理偶尔丢失的响应（通常通过重新请求内容或设置响应传输的定期计划）。发送到主机的消息块中的序列号字段始终比最后从主机接收的消息块的序列号大一。它不用于跟踪响应消息块的序列。
